# Database and migrations

Updated: 2026-10-26. Agreed: multiple lists per user, normalized users/lists/items, UUIDv4 identifiers, and SQLx migrations. Whole-list snapshots with revision checks are the initial save approach. M2 implements the initial schema, stable creation-order list positions, item row diffs, and embedded migrations. Production operational procedures remain planned for M11.

## Identifiers

Use UUIDv4 for users, lists, and items. Generate item IDs in the browser when a command creates an item, before saving it. The server generates user IDs; list IDs may be generated by the client for creation. Validate canonical UUID strings on the server and reject collisions without overwriting existing records.

UUIDv4 is standardized and does not require a central counter. Browser `crypto.randomUUID()` provides it in a secure context; local development should use localhost, and hosted access should use HTTPS. Do not implement a custom random ID generator. UUIDv7 is an alternative if time-ordered IDs become useful, but list order and creation timestamps must remain explicit fields regardless of the ID format.

Store IDs as canonical lowercase, hyphenated `TEXT` in SQLite and strings in JSON/API. This favors readable queries and simple serialization over the smaller size of 16-byte BLOBs. IDs are immutable and unique per entity table across users. They are identifiers, not authorization tokens. Creation timestamps are server-assigned UTC Unix milliseconds and must not be inferred from IDs.

Normal import creates fresh IDs. Explicit restore may preserve IDs only when there are no collisions. Export does not grant permission to restore ownership or account credentials.

## Relationships

```text
users 1 ─── N lists 1 ─── N items
                              │
                              └── parent_id → items in the same list
```

Each list has one owner; shared lists and membership tables are outside the current proposal. This supports multiple accounts in the schema without deciding registration, login, or public multi-user access. M2 provisions one local user resolved by the server without a login screen. All queries remain owner-scoped; a submitted owner ID is never treated as proof of identity. Production authentication is deferred to M11 before non-local deployment.

Prefer normalized item rows over the earlier single-JSON-column proposal. This makes ownership, structural constraints, and future item queries more explicit. The trade-off is more persistence logic. Do not keep an independently authoritative JSON copy alongside the rows. Nested JSON remains the API/export representation.

## Implemented schema

The authoritative definition is [the initial migration](../backend/migrations/20261026000100_initial_schema.sql). It creates users, lists, items, their indexes and constraints, and a `local_identity` singleton referencing the provisioned local user. [M4 installation identity](../backend/migrations/20261026000200_installation_identity.sql) adds a separate installation UUID; original migrations are unchanged. IDs and timestamps are supplied by the backend. Authentication tables remain deferred to M11.

The composite parent foreign key prevents parenting an item under another list. `parent_id = NULL` means a root item. The deferred constraint permits transactional inserts/reparenting in any order, but requires a valid tree at commit. Self-parenting is rejected by SQL; longer cycles, depth limits, and ownership authorization require application validation. SQLite foreign keys must be enabled on every connection before transactions.

Parent deletion does not rely on recursive foreign-key cascades: explicitly delete the entire branch in one transaction, then commit. Deleting a list cascades to all its items. Deleting a user is restricted until its lists are explicitly handled. Deletion UX and recovery beyond session undo remain undecided.

## Order and transactional saves

Start with integer `position` values `0..n-1` within each sibling group, and separately for a user's lists. Reindex affected groups within the write transaction. The server ensures contiguous unique sibling positions; the migration does not enforce uniqueness because bulk reorder would otherwise require temporary positions and special treatment of NULL root parents. Read with `ORDER BY position, id` as a deterministic fallback. IDs never determine intended order. Consider sparse ranks only if measured reorder costs justify them.

The agreed initial whole-list snapshot API works as follows: normalize the submitted nested tree into rows. Authorize ownership, validate the complete tree, compare-and-swap the list revision, apply a row diff, and update timestamps within one transaction. A revision mismatch or invalid item rolls back everything. Existing item IDs from another list/user must be rejected, never reassigned by a broad upsert. Preserve existing `created_at` for unchanged items. Every content change, including title changes, participates in revision checks.

List ordering is currently creation order: insertion allocates MAX(position)+1 atomically; deletion may leave harmless gaps. User-driven list reorder and its concurrent-update contract remain deferred. Moving branches between lists is not included in the current command set and would need an atomic operation covering both list revisions.

Configure foreign keys on every pooled connection, a finite busy timeout, and WAL for a single-host deployment after verifying backup behavior. Keep transactions short. M6b stores manual collapse preferences separately in SQLite; temporary expansion remains browser UI state. M4 adds an installation singleton with a generated UUID via a new additive migration for draft scoping. Authentication/session tables remain deferred to M11.

## Example: indent and outdent over the API

Moving the cursor changes only browser focus and sends no write. Tab/Shift+Tab invokes a local tree command immediately and adds an undo step. The autosave queue then sends the latest nested snapshot through the existing `PUT /api/lists/:id` contract. Several quick commands may be coalesced into one snapshot; saving is not a request per keypress.

Example before indent: root items `A`, `B`, `C`; `B` has child `D`. Indenting `B` under `A` produces roots `A`, `C`, with `B` as the last child of `A`; `D` remains under `B`.

Illustrative request using readable placeholder IDs:

```json
{
  "baseRevision": 12,
  "document": {
    "id": "list-1",
    "title": "Personal",
    "nodes": [
      {
        "id": "A", "kind": "item", "text": "A", "completed": false,
        "children": [
          {
            "id": "B", "kind": "item", "text": "B", "completed": false,
            "children": [
              {"id": "D", "kind": "item", "text": "D", "completed": false, "children": []}
            ]
          }
        ]
      },
      {"id": "C", "kind": "item", "text": "C", "completed": false, "children": []}
    ]
  }
}
```

Within one write transaction, the backend:

1. Checks the authenticated owner, validates the tree, and ensures all existing IDs belong to this list.
2. Conditionally increments `lists.revision` from 12 to 13, scoped by list ID and owner. If no row matches, distinguish missing/unauthorized access from an authorized stale revision; roll back and return the appropriate response.
3. Computes the row diff: `B.parent_id` becomes `A`, `B.position` becomes its new sibling index, and `C.position` changes from 2 to 1. `D.parent_id` stays `B`; its row does not need rewriting. Existing siblings of `A`'s children may need position updates depending on the operation.
4. Updates affected rows/timestamps and commits. Success returns revision 13; validation, constraint, or write failure must explicitly roll back both the move and the revision change. A deferred foreign-key failure can occur at commit; the transaction wrapper must handle commit errors and roll back as well.

Shift+Tab uses the same pipeline: the branch root becomes a sibling immediately after its former parent, affected sibling positions are recalculated, and its descendants remain attached. No recursive copying or ID changes are needed. A request that only moves a branch must not delete and recreate it.

The response acknowledges the submitted snapshot only. If the user has edited again during the request, keep the newer local state and send it next using revision 13. A stale base revision returns a conflict rather than silently applying a move to a different tree.

A future operation-based endpoint could accept `move_item` with `itemId`, `newParentId`, and `afterSiblingId`, plus a base revision and idempotency key. That reduces payload size, but adds command validation and retry semantics. Protocol and transfer-size optimization belongs to M14; snapshot transfer does not require replacing all database rows.

## Migration files and database history

Agreed tooling: SQLx for SQLite access and migrations with the Rust stack. Keep SQL source files in the repository:

```text
backend/
  migrations/
    20261026000100_initial_schema.sql
    20261026000200_add_example_feature.sql
```

The second filename illustrates naming only; it is not a planned feature. Use unique sortable versions with descriptive names. Include migrations in the compiled server with `sqlx::migrate!("./migrations")`, relative to the backend Cargo project. Ensure Cargo rebuilds when migration files are added or changed, using the build-script approach documented by SQLx. Preserve LF line endings for SQL files through a future `.gitattributes` entry.

SQL files are the source of truth for changes. SQLx keeps applied versions and checksums in its migration history table, `_sqlx_migrations` by default. Do not manually maintain a second schema-version table or edit migration history to suppress mismatches. Database migration versions, API revisions, and JSON `schemaVersion` are separate concepts.

Once applied to a persistent/shared database, a migration is immutable: add a new migration to change it. Prefer forward-only corrections. Destructive down migrations are not a backup strategy; recovery may require a compatible binary and a verified pre-upgrade backup.

## Applying and verifying migrations

Implemented: `make db-migrate` runs the backend with `--migrate`; ordinary server startup applies the same embedded migrations and provisions the local identity. Use `FMN_DB_PATH` to choose the database. `make docker-migrate` remains planned with M11 deployment. No SQLx CLI is required.

For deployment: stop writes, make and verify a consistent backup, run migrations through one process, then start the compatible server. On migration failure, do not serve requests against an uncertain schema. Keep pending/mismatched migration checks in startup; avoid independently maintained SQL between startup and manual commands. The server should refuse a database newer than its supported migration set.

Use transactional migrations where supported. SQLite table rebuilds or changes requiring foreign-key PRAGMA adjustments need a separately designed procedure; do not switch foreign keys off inside an already active transaction and assume it worked. Large backfills may need a staged migration rather than one long startup transaction.

Before release, verify migration from an empty database and upgrade from the previous supported schema with representative data. Check row counts, owner/list isolation, parent constraints, completion checks, revisions, and `PRAGMA foreign_key_check`. Verify a failed migration cannot result in serving a partially upgraded database. Run `PRAGMA integrity_check` and a restore check on the backup as appropriate for the upgrade.

## Item tags — M8

[The additive M8 migration](../backend/migrations/20261028000500_item_tags.sql) adds `items.tags TEXT NOT NULL DEFAULT '[]'`. Rust independently validates array count, names and duplicates, then stores compact JSON through ordinary owned-list row-diff transactions. Tags inherit ownership from their item/list; no global tag registry or shared IDs are introduced. Existing notes/content IDs/revisions and saved view metadata are unchanged. JSON v3 preserves tags; older inputs cannot silently carry unknown tag fields.

## Item notes — M7

[The additive M7 migration](../backend/migrations/20261027000400_item_notes.sql) adds `items.note TEXT NOT NULL DEFAULT ''`. Existing items retain their content and receive empty notes. Notes use existing owned-list snapshot transactions, row-diff updates, content revisions and deletion cascade. They have a 64 KiB UTF-8 validation bound; view-preference metadata and revision are independent.

## View-state metadata — M6b

[The additive M6b migration](../backend/migrations/20261027000300_list_view_states.sql) adds a unique owned-list index and `list_view_states`, keyed by `(user_id, list_id)`, with JSON collapsed-ID text and an independent nonnegative revision. Its composite foreign key enforces list ownership and cascades on list deletion. No existing list/item fields or applied migrations are changed.

Owned GET returns current branch IDs with stale IDs filtered, defaulting to an empty set/revision zero when no row exists. PATCH compares the separate revision and applies explicit per-ID collapsed booleans in a transaction. It starts with a no-op owned-list write to obtain the SQLite write lock without incrementing content revision or timestamps. Stale IDs are pruned and only current same-list branches can be collapsed. Unknown IDs are ignored without exposing other lists. Malformed IDs or excessive changes are rejected. This metadata is absent from JSON/Markdown exports; database backups include it.

## Due dates — M10

`20261028000600_item_due_dates.sql` adds nullable `items.due_date TEXT`. Existing items receive NULL. The API/portable field is optional `dueDate`; both languages validate real Gregorian YYYY-MM-DD dates, years 0001–9999. Ordinary owned row-diff transactions update dates and content revision atomically. JSON v4 preserves dates; collapse preferences and their revisions remain independent.

## Accounts and sessions — M11

`20261028000700_authentication.sql` adds `auth_accounts` keyed by existing users, library-compatible `tower_sessions` records, owned `auth_grants` with auth version/idle/absolute lifecycle, and bounded durable `auth_attempts`. It changes no existing content rows or owner IDs. Password reset/version changes and grant revocation are transactional. Library schema creation is integrated in SQLx migration history, not run through an independent `migrate()` method. Account credentials, session records and attempt buckets are excluded from content JSON; installation backups contain them. See [Authentication](authentication.md).

## Account administration — M11a

`20261029000800_account_administration.sql` preserves existing credentials/grants while adding activated_at and disabled_by_admin metadata, digest-only purpose/version-bound account_tokens, and actor/target account_audit rows. Pending credentials use an empty hash and disabled authentication state until atomic redemption. Disabling/reissue/reset/revocation change the account version and invalidate grants/links in the same transaction. These tables are not portable content JSON. See [Account administration](account-administration.md).

## Native backup and restoration — R1

Maintenance opens source files read-only without Store::open. Verified VACUUM INTO candidates are published exclusively to fresh paths; restore applies supported migrations only to its candidate and rotates installation/authentication state before publication. No new schema migration is required. Existing applied SQL remains unchanged. See [Backup and restore](backup-restore.md).
